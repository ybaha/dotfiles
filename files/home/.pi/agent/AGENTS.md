# Personal Pi operating rules (all working directories)

- Follow the current repository's `AGENTS.md` and local instructions for project-specific work. Do not assume optional repositories exist on this machine.
- hc (herdr-core) owns durable terminals; Ovis/herdr-app group them into workspaces/tabs using `herdr.space`/`herdr.tab` and `ovis.*` labels. Pi owns the agent session; pi-subagents are temporary children, not durable terminals. Use one durable agent per terminal and one writer per worktree unless the user requests otherwise. `$HC_TERMINAL_ID` is your terminal address, not a legacy pane ID.
- Do not open new visible workspaces/tabs/terminals for routine helpers; reuse the existing durable agent or use a Pi background subagent. `/skill:worktree` and `/skill:lead` may create labeled hc terminals only when the user requests independent durable worktrees/workers. Start anything that must survive its caller with `hc run --bg --no-parent`. Do not close or reorganize terminals/windows without explicit approval. Chief/Telegram sessions are disabled pending an hc port; there is no Chief UI exception.
- Keep the main session responsive: start subagents with `run_in_background: true`, continue independent work, and use completion notifications rather than polling or `get_subagent_result(wait: true)`. If only child results remain, give a short status and yield instead of waiting inside a tool. Use blocking calls only for a genuine immediate dependency when no useful parallel work is possible.
- Consult `hc --skill` and `hc <command> --help` before controlling persistent terminals; use `herdr-app --skill` for window arrangement. Do not assume the old `herdr` CLI, pane IDs, socket variables, integration installers or workflow plugins exist. hc observes program status directly; never force input through blocked permission dialogs.
- Use `/skill:worktree` for an explicitly requested isolated git worktree and labeled hc terminal when available. Its source is the global skill in the dotfiles repo. Keep the existing `~/.herdr/worktrees/<repo>/<slug>` location; do not move/delete existing directories.
- For one lead delegating to several worktree workers, use `/skill:lead`.
- Where configured, use `claude-bridge` for Claude (not the direct Anthropic API), `cursor-ide/composer-2.5` for approved implementation (not Cursor's agent CLI or fast variant), and MiniMax only for fixed-scope mechanical tasks with review. Before substantial delegation, check quota with `bash ~/.pi/agent/extensions/quota-status.sh` and verify the selected provider is available.
- Keep the machine responsive: run tests one-shot (`vitest run`, `CI=1`), never in watch mode; wrap long commands in `timeout`; do not background jobs with `&` or pipe them to `tail`; and do not start a test run if one for the same project is already running (check with `pgrep`). Stop every process you start before finishing, and never stop one you did not start.
- Do not put credentials in repositories or prompts. Keep Pi auth local in `~/.pi/agent/auth.json`. Ask before installing/updating integrations, packages, or plugins on a machine.
- Tailnet directory: `http://agents/` lists every durable home-cluster and dev service with URL, auth location and examples (agents: `/index.md`, `/services.json`, `/status.json`). Look there before guessing a URL or port. When you add, move or remove a front end/API reachable on the tailnet (Tailscale Serve, LXC/VM service, durable dev tool; not temporary `/preview` URLs), update `directory/registry.toml` in the dotfiles repo and run `directory/deploy` in the same task if both exist on this machine. List where credentials live, never the credentials.

When relevant, consult the short guides in the dotfiles repo's `docs/agent-stack/`; do not load them for every task.
